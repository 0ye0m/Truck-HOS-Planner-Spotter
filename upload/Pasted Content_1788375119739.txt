============================================================
14. HOS RULES
============================================================

Model the assessment's specified property-carrying driver scenario:

- 70-hour / 8-day cycle
- 11-hour driving limit
- 14-hour window
- 30-minute break after 8 cumulative driving hours
- 10 consecutive hours off duty for the modeled daily reset
- 34-hour restart when the modeled cycle is exhausted
- pickup = 60 minutes on duty
- dropoff = 60 minutes on duty
- fuel stop = 30 minutes on duty
- fuel planning at least every 1,000 route miles
- no sleeper split in this version
- no adverse-driving exception
- no team driving
- no short-haul exception

Keep these assumptions centralized.

DO NOT duplicate constants across multiple files.

Example:

HOS_RULES = {
    driving_limit_minutes: 660,
    duty_window_minutes: 840,
    break_threshold_minutes: 480,
    break_duration_minutes: 30,
    daily_reset_minutes: 600,
    cycle_limit_minutes: 4200,
    restart_minutes: 2040,
    fuel_interval_miles: 1000,
    pickup_duration_minutes: 60,
    dropoff_duration_minutes: 60,
    fuel_duration_minutes: 30
}

Use descriptive names.

============================================================
15. HOS SIMULATION STRATEGY
============================================================

Implement the schedule as a simulation.

Track state such as:

- elapsed time
- driving time in current window
- duty time/window
- cumulative driving since break
- cycle hours used
- miles since fuel
- current route position
- current trip leg
- current status

At every transition, determine the next legal event.

DO NOT simulate minute-by-minute unless there is a compelling reason.

Use event-based simulation.

Calculate how much driving can safely occur before the next constraint.

Possible next boundaries:

- destination
- pickup
- dropoff
- fuel threshold
- 8-hour break threshold
- 11-hour driving threshold
- 14-hour window expiry
- cycle exhaustion

Advance directly to the next boundary.

This makes the engine efficient and deterministic.

============================================================
16. RULE PRIORITY
============================================================

When multiple constraints can trigger, establish explicit priority.

The priority must be documented in code and tested.

Never rely on accidental if/else ordering.

The engine must never:

- exceed 11 driving hours
- exceed the modeled 14-hour window
- exceed the modeled 70-hour cycle
- drive beyond a required break
- miss a required fuel stop
- create overlapping events
- create negative-duration events
- create gaps in daily logs

============================================================
17. 30-MINUTE BREAK LOGIC
============================================================

Implement carefully.

A qualifying non-driving period of at least 30 minutes can satisfy the modeled
break requirement.

Pickup, fuel, or another qualifying non-driving event can therefore satisfy
the break requirement if the event duration qualifies.

Do not incorrectly insert another 30-minute break immediately afterward.

Maintain an explicit break accumulator.

Two separate 15-minute stops must NOT automatically be treated as one
30-minute qualifying break.

Write tests for this.

============================================================
18. FUEL STOP LOGIC
============================================================

Fuel planning must be route-distance based.

Track:

miles_since_fuel

When the threshold approaches:

schedule fuel before exceeding the configured interval.

Fuel should reset:

miles_since_fuel = 0

Fuel stops must appear consistently in:

- backend schedule
- map
- timeline
- daily logs
- summary counts

Never create a fuel stop in one subsystem but forget it in another.
